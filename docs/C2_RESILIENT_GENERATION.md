# C2 — עמידות היצירה לניתוק

**הבעיה (מהביקורת, §2):** החצי היקר של הצינור רץ בתוך בקשת ה-HTTP של הלקוחה.
משתמשת שנועלת את הטלפון בשנייה 30 מבטלת את ה-invocation אחרי שהקריאה למודל
התמונה כבר חויבה — ואז אין שורת `generation_runs`, אין גרסה, והכסף יצא לריק.
`waitUntil` נוסה (#61) ולא רץ בפרודקשן: כל יצירה נתקעה על `stage=rendering` בלי
שום שורה נכתבת. ההערה בראש `src/app/api/generate/route.ts` מתעדת את זה.

**העיקרון:** מי שעושה את העבודה היקרה הוא גם מי שמחזיק את התוצאה. הקופסה כבר
מריצה את הרנדר, החיתוך והווקטוריזציה — היא צריכה גם לזכור מה יצא, כדי שבקשה
שנייה תוכל לאסוף את התוצאה במקום לשלם עליה שוב.

---

## 1. שינוי החוזה בין ה-Worker לקופסה

היום: `POST /api/generate` הוא קריאה סינכרונית אחת שנמשכת עד 240 שניות. אם
החיבור נקטע — הכול אבד.

מכאן: הקופסה מחזיקה את ההרצה תחת **מזהה שה-Worker קובע**.

| | היום | מכאן |
|---|---|---|
| `POST /api/generate` בלי `job_id` | מריץ, מחזיר את התוצאה | **ללא שינוי** (תאימות לאחור לחלון הפריסה) |
| `POST /api/generate` עם `job_id` | — | 202 `{job_id, state:"running"}` מיד; ההרצה ממשיכה ברקע |
| אותו `job_id` שוב, בזמן ריצה | — | 202 `{state:"running"}` — **לא מתחיל הרצה שנייה** |
| אותו `job_id` שוב, אחרי סיום | — | 200 עם התוצאה השמורה — **בלי קריאה נוספת למודל** |
| `GET /api/generate/{job_id}` | — | `{state, result?, detail?}` |

המזהה שהקופסה מקבלת חייב להיות **דטרמיניסטי** מצד ה-Worker: זו כל הנקודה. אם
המזהה מוגרל בכל בקשה, בקשה חוזרת מייצרת job חדש ומשלמת שוב.

## 2. מזהי הניסיון בצד ה-Worker

`jobId` מגיע מהלקוחה ויציב על פני ניסיונות חוזרים (הוא נשמר ב-`pendingJob`).
מזהה הניסיון נגזר ממנו בגזירה טהורה:

```
attemptId = uuid( sha256("forme-generation-attempt:" + jobId + ":" + attemptNo) )
```

מה שזה קונה, מעבר לזיהוי ה-job על הקופסה:

- **נתיבי ההדמיות דטרמיניסטיים.** היום הם `renders/<design>/<Date.now()>-<i>.png`,
  כלומר בקשה חוזרת כותבת למקום אחר ומאבדת את הקשר לתוצאה שכבר הועלתה. מכאן הם
  נגזרים מ-`attemptId`, שנשאר שונה בין ניסיון ראשון לשני — התכונה שבגללה ה-stamp
  נוסף מלכתחילה.
- **`generation_runs.id` יציב.** הרצה שהתחדשה מעדכנת את אותה שורה במקום לפזר
  שורות יתומות ביומן. לכן `persistRun` הופך ל-upsert.

## 3. הזרימה

```
POST /api/generate {designId, jobId, ...}
  │
  ├─ בעלות, מידות, מכסה          ← ללא שינוי
  ├─ createJob(jobId)             ← מותר לחדש job רץ של אותו עיצוב (ראה §4)
  │
  ├─ attemptId = derive(jobId, 1)
  ├─ POST box /api/generate {job_id: attemptId, ...}
  │     ├─ 202 running → סקירה עד סיום
  │     └─ 200 done    → התוצאה כבר בקופסה (זו בקשה מתחדשת) ✔ לא שולם שוב
  │
  ├─ persistRun(attemptId)  ← upsert
  ├─ framing + ולידציה + ingestCutouts  (החצי הזול)
  └─ finishJob(jobId)
```

ניתוק בכל נקודה אחרי שהקופסה התחילה: הקופסה ממשיכה, שומרת, ומחזיקה את התוצאה
עד ה-TTL. הבקשה הבאה עם אותו `jobId` נכנסת ב"200 done" ומסיימת את השמירה.

## 4. חידוש job קיים

`createJob` זורק היום `JobConflictError` על כל התנגשות מפתח, וה-route מתרגם ל-409.
הנימוק נכון — `jobId` מגיע מהלקוחה, והתנגשות עשויה להיות ניסיון לדרוס הרצה של
אחר. אבל הוא רחב מדי: הוא חוסם גם את החידוש הלגיטימי.

הכלל מדויק יותר: **מותר לחדש job שהוא `running` ושייך לאותו עיצוב שהפונה כבר
עבר עליו `requireDesignAccess`.** תוקף לא יכול להגיע לשם — הוא ייחסם על העיצוב.

### 4.1 job שהסתיים — התוצאה שם, ומי שקורא אותה הוא ה-POST (AP-0090)

הכלל למעלה נכתב עם "job שהסתיים עדיין מחזיר 409: התוצאה שם, שיקרא אותה" —
ובפועל לא היה מי שיקרא. ה-POST זרק 409 גנרי, ומסלול ההתאוששות בלקוחה
(`mayHaveSurvived`) מופעל רק על status 0 / גוף קטוע / 5xx בלי קוד. 409 הוא 4xx,
ולכן הוא הלך ישר למסך השגיאה.

זה נמדד על AP-0090: הבקשה נקטעה אצל הלקוחה (ניתוק — ולכן היא **שומרת** את
ה-`jobId`, כמתוכנן), השרת המשיך וכתב `done` על השורה, והניסיון החוזר קיבל
"משהו השתבש". הלחיצה הבאה יצאה עם מזהה חדש — כי 409 היא תשובת שרת ולכן מנקה את
המזהה — והריצה את הכול מחדש: עוד קריאה למודל, עוד יחידת מכסה, ועוד גרסה על
אותו עיצוב, בזמן שהתוצאה ששולמה ישבה בטבלה.

מכאן `JobConflictError` נושאת את השורה שנמצאה, וה-POST מכריע לפיה
(`replayFinishedJob`):

| השורה הקיימת | התשובה |
|---|---|
| `running`, אותו עיצוב | חידוש — ההרצה נמשכת (§4) |
| `done` עם `result`, אותו עיצוב | **200 עם התוצאה השמורה**, בלי קריאה למודל |
| `error`, אותו עיצוב | **הקוד המקורי** (`content_blocked`, `bad_size`…) ולא "משהו השתבש" |
| עיצוב אחר / שורה שנעלמה / `done` בלי `result` | 409 — שם ההתנגשות אמיתית |

השריון (`generation_reservations`) מזוהה ב-`runId` שנגזר מה-`jobId`, ולכן שידור
חוזר אינו צורך יחידת מכסה שנייה. `notifyDesignReady` אינו נשלח בשידור חוזר: מי
שכתב `done` כבר שלח אותו.

## 5. מה נשאר פתוח (מכוון, לא נשכח)

- **חידוש אוטומטי בלי הלקוחה.** ה-GET של `/api/generate/<jobId>` יכול היה
  לאסוף את התוצאה מהקופסה בעצמו, אבל הוא לא מחזיק את ההקשר (פרומפט, תכנון,
  גשרי הכיתוב) — הוא היה דורש הקפאה של ההקשר בשורת ה-job. כרגע החידוש נשען על
  בקשה חוזרת של הלקוחה עם אותו `jobId`, שנושאת את הגוף המקורי.
- **restart של הקופסה** מאבד הרצות שבאוויר (התוצאה נכתבת לדיסק רק בסיום).
  הרצה שהסתיימה שורדת restart.
- **תקרת מקביליות** על הקופסה — לא נוגעים בה כאן; היא בסעיף הווקטורייזר בדוח.
